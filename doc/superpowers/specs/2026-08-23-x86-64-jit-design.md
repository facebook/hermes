# Design: the x86-64 JIT backend

## Scope and goals

A second JIT backend targeting x86-64 SysV (Linux, macOS, Android
emulators, server-side Hermes). Windows x64 is explicitly out of scope —
neither backend supports it today; both will need it eventually, and this
design avoids gratuitously blocking it (the register convention and ABI
assumptions live in one place per backend) without designing for it.

Both heap modes are supported from the start: HV64, and HV32 (compressed
pointers with contiguous heap), matching the arm64 gate. Android emulators
run what ships on Android — HV32 — so an emulator-targeted backend that
only did HV64 would be testing the wrong configuration.

The fast/slow-path structure (what is inlined, what calls a runtime
helper, how ICs tier) is a property of the runtime model, not the ISA, and
carries over from arm64 unchanged. Only instruction selection is
per-CPU. Success for v1 is: full `test/jit` plus the differential stress
matrix passing natively under ASan, in both heap modes, with perf "sane";
a measured perf-tuning pass comes after.

## Register convention

| Role | arm64 | x86-64 SysV |
|---|---|---|
| xRuntime | x19 | r15 (callee-saved) |
| xFrame | x20 | r14 (callee-saved) |
| Native frame pointer | x29 (+x30 record) | rbp (`push rbp; mov rbp, rsp`) |
| GPR globals | x21–x28 (8) | rbx, r12, r13 (3) |
| Vector globals | d8–d15 (8) | none (see below) |
| GPR temps (`TempRegAlloc`) | x0–x15 (16) | rax, rcx, rdx, rsi, rdi, r8, r9, r10 (8) |
| Vector temps | d0–d7, d16–d31 (24) | xmm0–xmm15 (16) |
| Reserved scratch, never allocated | x16, x17 | r11 |
| Helper args / return | x0–x7 / x0 | rdi, rsi, rdx, rcx, r8, r9 / rax |

The helper argument registers sit inside the temp pool exactly as x0–x7 do
on arm64, so `callRuntime`'s sync/free discipline carries over
unchanged. r11 takes the x16/x17 role: assert and instrumentation
emission, call-target materialization — anything that must not disturb
`TempRegAlloc` state. r11 is the traditional linker scratch and never
carries an argument. rsp stays 16-byte aligned at every call site: the
fixed frame (after the `push rbp`) is sized to a multiple of 16. No
red-zone use — emitted code makes calls, so the red zone is unusable
anyway.

rbp is a real frame pointer, not a fourth global. Native unwindability
through JIT frames (debugger backtraces, `perf` with jitdump, crash
reports) matters on every target this backend exists for; a 33% bump to
the scarcest register class does not outweigh it.

### Number globals: callee-saved GPRs only

SysV has zero callee-saved vector registers, so arm64's "number FRs live
in d8–d15 for the whole function" mechanism has no direct equivalent. The
chosen design: the global-assignment loop hands out the three callee-saved
GPRs to number and non-pointer FRs alike. A number FR's global holds the
double as raw 64 bits; arithmetic does `movq xmm, gpr` / `movq gpr, xmm`
(1–2 cycles each way, once per FR per BB with local caching — cheaper than
a frame round trip, and the value survives calls). This is not new
machinery: it is arm64's existing overflow behavior (number FRs spill into
GpX globals when VecD runs out) promoted to the only case. The FR model,
its invariants, and the eligibility rules from the bytecode header's
number/non-pointer register counts are unchanged; there is simply one
global register class instead of two.

Alternatives considered and rejected for v1:

- **Frame-resident numbers with per-BB xmm caching only.** Loses register
  residency for exactly the bread-and-butter case: loop-carried variables
  reload from the frame at every BB boundary and after every call.
- **Vector globals by private convention** (reserve xmm8–15, spill live
  ones to their frame slots around every emitted call). Preserves the
  arm64 two-class shape and is free in call-free code, but: (a) the cost
  placement is backwards — real callee-saved registers charge the callee
  once per activation and only if used, while this charges every call site
  of every caller per call executed, and unconditional JS→JS calls are the
  hot path; (b) it weakens the load-bearing invariant that a global
  register is valid whenever `globalRegUpToDate`, adding "unless inside a
  call window" to every consumer, including the type-assert read
  protocol; (c) it halves the vector temp pool while still requiring the
  GPR-global machinery. A targeted refinement — xmm globals only for
  functions whose fast paths contain no unconditional calls, with
  spill/reload confined to cold out-of-line slow paths — is recorded as
  future work if profiles ever show FP-dense call-light loops suffering.

## Source tree and sharing strategy

New parallel tree `lib/VM/JIT/x86-64/` plus
`include/hermes/VM/JIT/x86-64/JIT.h` (the dispatcher in
`include/hermes/VM/JIT/JIT.h` already expects that path and
`namespace x86_64`), mirroring the arm64 file split one-for-one:
`JIT.cpp`, `JitEmitter.h`, `JitEmitter-{internal,regalloc,alloc,const,
object,property,call,env,array,arith,control}`, `JitImpl.h`.

Sharing is decided by *how* a piece is shared, not by wish:

- **Shared by construction: the Compiler decode driver.** It reads
  bytecode operands (arch-independent by definition) and forwards to
  `Emitter` methods; even its asmjit types (`asmjit::Label`) are
  core-asmjit, not per-arch. It moves to a shared `.cpp` under
  `lib/VM/JIT/`, compiled once against the current arch's emitter via a
  small dispatch header (`JitCurArch.h` defines `HERMESVM_JIT_ARCH_NS`
  and includes the arch's emitter headers under the same `#if`s as
  `JIT/JIT.h`; the driver is compiled inside that namespace, so the
  Compiler stays a nested private class of the arch's `JITContext` with
  zero identifier changes -- a `using` alias cannot express a nested
  class). Not a template: only one arch is ever compiled per binary, and
  the namespace-macro form keeps it an ordinary debuggable class; the
  template conversion is trivial if a both-arches-in-one-binary harness
  is ever wanted. This extraction happens as a prep refactor on the arm64
  side **before** x86-64 work begins, gated on byte-identical arm64
  emission (qemu + goldens). Side effect: the emitter method surface — the
  porting contract — becomes compiler-enforced, and x86-64 bring-up starts
  from an all-stubs `Emitter` where every unimplemented method calls
  `unsupported()` (longjmp to don't-JIT, the existing mechanism).
- **Shared by likelihood: everything else conceptually common.** The FR
  model and `TempRegAlloc` (`JitEmitter.h`, `-regalloc.cpp`), slow-path/
  catch-table/RO-data emission, `JitImpl.h`, the type-assert machinery:
  same shapes and invariants, but `HWReg` encoding, the global-assignment
  loop, and the LRU pools legitimately differ. These are **copied and
  rewritten in place**; forcing sharing here would constrain both
  backends. Extraction of whatever remains identical happens after both
  backends have settled, from two working instances. Where a copied file
  diverges for a reason (not just encoding), the site gets a
  `// x86-64:` comment so the eventual extraction pass is grep, not
  archaeology.
- **Already shared, used as-is:** DiscoverBB, RuntimeOffsets, JitHandlers,
  JitCounters, PerfJitDump, and the `_sh_ljs_*` runtime helpers.
- **Interface contract, not sharing:** `x86_64::JITContext` stays
  method-for-method identical to `arm64::JITContext` — the interpreter and
  ConsoleHost compile against whichever the dispatcher picks. Its methods
  (`compileImpl` policy, `markRoots`, `dumpCounters`) are duplicated
  per-arch for now; they are small, entangled with each arch's `Impl`, and
  in the extract-later bucket.

## Emitter specifics

**Baseline ISA: AVX, gated by CPUID.** Legacy SSE scalar FP is
two-operand and destructive, forcing every FP emitter through a
copy-then-operate shim with aliasing hazards (dst aliasing src2 is
clobbered by the initial mov). VEX encodings are three-operand
(`vaddsd dst, src1, src2`), so the FP emitters — most of the arithmetic
surface — mirror the arm64 code shape one-for-one with no hazard
class. AVX is universal on every stated target (anything since 2011); on a
non-AVX CPU a CPUID check at `JITContext` construction leaves the JIT
disabled and the interpreter carries on — no crash, no build split, the
existing `enabled_` mechanism. VEX is used consistently for all vector
instructions; legacy-SSE encodings are never mixed in (transition
stalls). Integer ops remain two-operand regardless; a small `emit3op`
helper in `-internal.h` encapsulates mov+op+aliasing so emitter bodies
stay three-operand in shape.

Idiom mappings (details verified at implementation time; the spec fixes
the approach):

- **Frame addressing:** `[r14 + disp32]` reaches every frame slot; the
  `isAddSubImm`/`emit_add_imm_u24` fallback family has no equivalent and
  is not ported.
- **RO data:** RIP-relative `disp32` reaches data appended to the code
  block by construction; the `ldr`-literal range machinery is not ported.
- **Tag tests:** same NaN-box algebra; `sar`/`shr` by 47–48 plus `cmp`
  replace `asr` plus `cmn`. The implementation carries a mapping table
  from each arm64 tag-test helper to its x86 sequence.
- **NaN-aware conditions:** `ucomisd` reports unordered as ZF=PF=CF=1, so
  above-family conditions (`ja`/`jae`) are NaN-safe-false, below-family
  are not, and `jp` takes over arm64's `b.vs` routing role. The full
  condition mapping table is written down in `-internal.h` next to its
  helpers and covered by type asserts from day one.
- **Calls:** `movabs r11, imm64; call r11` (the reserved scratch doing its
  job); direct `rel32` calls are not assumed reachable.

## Testing

The backend is developed natively under the repo-default ASan+Debug
build — the "no ASan under qemu" limitation of arm64 development on this
host does not apply, and `HERMESVM_SANITIZE_HANDLES` runs at full speed.

- **Differential matrix:** `aarch64/jit-stress.js` must print identically
  across {interpreter, arm64 JIT (qemu), x86-64 JIT (native)} × {HV64,
  HV32, BOXED} × {± `-Xjit-emit-type-asserts`}. BOXED forces the
  boxed-double paths on a 64-bit host — where HV32 emitter bugs hide.
- **Golden tests split by arch:** `test/jit/` keeps all behavior-checking
  tests arch-neutral; emitted-code goldens move to `test/jit/arm64/` and
  grow siblings in `test/jit/x86-64/`, gated by a new lit feature
  `jit_arch` (derived from the target processor in CMake, next to
  `jit_enabled`). Golden files are full-line asm listings; interleaving
  two ISAs via CHECK prefixes was rejected as unmaintainable. Duplicating
  the small JS sources between arch dirs is acceptable — a golden's JS
  exists only to pin emission.
- **Stubs-first ratchet:** the full `test/jit` suite runs from milestone 1
  (unimplemented opcodes fall back to the interpreter); progress is
  measured by how much of `jit-stress.js` compiles under
  `-Xjit=force -Xjit-crash-on-error`, not a hand-kept checklist.
- **Cross-arch oracles are behavioral:** the differential matrix, the JIT
  counters (`NumCall`/`NumCallSlow` should match across backends for the
  same workload — an arch-neutral decision-level signal), and the type
  asserts. `jit-diff.sh` remains same-arch tooling: it gates the arm64
  prep refactor (byte-identical) and regression-checks x86-vs-x86 during
  development. Cross-arch, `jit-dump.sh` output is a side-by-side reading
  aid while writing emitters, not a diffable artifact.
- **CI shape:** native x86-64 {ASan+Debug HV64, ASan+Debug HV32, Release
  HV64} × (`test/jit` + stress), plus the existing qemu arm64 job as the
  cross-check.

## Build gating

`Config.h` gains the x86-64 arm: `HERMESVM_JIT=1` when
`__x86_64__`/`_M_X64`, not Windows, same heap condition as arm64 (no
compressed pointers unless contiguous heap), existing Apple clause
(macOS/Mac Catalyst only) unchanged. CMake keeps the current pattern: both
arch subtrees are listed under `HERMESVM_ALLOW_JIT` and every file
self-guards with `#if HERMESVM_JIT` plus its arch test — no CMake
arch-dispatch logic. The AVX CPUID check is runtime, not build-time.

As implemented, `Config.h` defines `HERMESVM_JIT_ARM64` /
`HERMESVM_JIT_X86_64` selectors and each arch-specific translation unit
guards on its own selector; shared files guard on `HERMESVM_JIT`.

## Bring-up milestones

0. **arm64 prep:** extract the shared Compiler driver (`JitCurArch.h`
   dispatch). Gate: byte-identical arm64 emission via qemu + goldens.
1. **Skeleton:** Config/CMake/tree, all-stub `Emitter`, `enter`/`leave`,
   param/const loads, `Ret`. An empty function JITs and returns; all else
   falls back.
2. **Arithmetic, comparisons, branches:** the NaN-routing table plus its
   type asserts; the arith sections of `jit-stress.js` under
   `-Xjit=force -Xjit-crash-on-error`.
3. **Calls, environments, closures:** the SH ABI frame dance.
4. **Property access + ICs, literals, young-gen allocation:** the
   GC-facing milestone; HV32/BOXED differential runs become load-bearing.
5. **Exceptions, switches, iterators/generators, `arguments`:** full
   `jit-stress.js` and full `test/jit` green.
6. **x86-64 goldens, perf sanity pass, CI matrix wiring.**

## Future work (recorded, not designed)

- xmm globals for functions whose fast paths contain no unconditional
  calls (spill/reload confined to cold slow paths).
- An arch-neutral emission-trace mode (one line per bytecode instruction:
  opcode, tier chosen, slow path emitted) for automated decision-level
  cross-arch comparison, if perf gaps ever call for it.
- Windows x64, in both backends.
- Extraction of the shared-by-likelihood pieces once both backends have
  settled.
