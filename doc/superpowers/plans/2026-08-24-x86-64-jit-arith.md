## The NaN-safe condition mapping (binding design, used by Tasks 1-3)

After arm64's `fcmp`, the codes kGT/kGE/kMI/kLS are all false on
unordered, and `b.vs` routes unordered (i.e., at least one non-number,
since non-numbers are NaN-boxed; `HERMESVALUE_VERSION == 2`) to the slow
path. x86's `vucomisd` sets ZF=PF=CF=1 on unordered, so only the
above-family conditions are unordered-false. Therefore:

| Comparison | arm64 | x86-64 |
|---|---|---|
| greater | `fcmp L,R` + kGT | `vucomisd L,R` + `a` (ja/seta) |
| greaterEqual | `fcmp L,R` + kGE | `vucomisd L,R` + `ae` |
| less | `fcmp L,R` + kMI | **`vucomisd R,L`** (swapped) + `a` |
| lessEqual | `fcmp L,R` + kLS | **`vucomisd R,L`** (swapped) + `ae` |
| equal (numbers) | `fcmp` + kEQ after `b.vs` routing | `vucomisd L,R` + `e` after `jp` routing |
| unordered routing | `b.vs lab` | `jp lab` |
| inverted jumps | `b(negateCond)` after `b.vs` | inverse cc (`be`/`b`/`ne`) after `jp` |

Consequences, mirrored from the arm64 logic:
- The non-inverted `jCond` may branch on its condition BEFORE the
  unordered routing (unordered-false makes that safe) — keep arm64's
  ordering: direct branch, then `jp slowPath`, then (inverted case only)
  the inverse-condition branch.
- The emitter signatures that take `a64::CondCode` take an
  `x86::CondCode` from {kA, kAE, kE} **plus a `bool swapOperands`**;
  the DECL_COMPARE/DECL_JCOND macro tables in `JitEmitter.h` supply both
  per operation. `invert` handling stays structural (same branches as
  arm64), never by picking a NaN-unsafe code.
- `setcc` writes an 8-bit register: clear the destination first
  (`xor r32,r32` before the compare, or `movzx` after) — pick one idiom
  and use it everywhere.

  var c = 0;
  while (n > 0) { n -= 1.5; c++; }
  return [n, c];
}

  for (var i = 0; i < limit; ++i) {
    if (i * i >= threshold) return i;
  }
  return -1;

  var s = 0;
  for (var i = 0; i < n; ++i) {
    var v = i % 3 === 0 ? NaN : i;
    if (v < 100) s += 1;
    if (!(v < 100)) s += 1000;
  }
  return s;
}
