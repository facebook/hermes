arm64 only; the x86-64 backend carries the one-line fix already.

ReifyArguments replaces the lazy-arguments register's undefined with an
Arguments object, but arm64's reifyArgumentsImpl
(lib/VM/JIT/arm64/JitEmitter-array.cpp) never updates the register's
recorded FR type. It stays OtherNonPtr from the initial
LoadConstUndefined (recorded by the shared driver's loadConstBits64), and
that stale claim licenses strictEqualImpl's raw-bit fast tier on a
register holding an object.

Today this cannot produce wrong results: bit equality is object identity,
and the register only ever holds undefined or that one Arguments object.
It is also not a GC hazard (the register class never gets a callee-saved
home). But the recorded type is false, and anything future that trusts
it harder inherits the problem.

Fix: mirror the x86-64 side - one compile-time bookkeeping line,
frUpdateType(frLazyReg, FRType::UnknownPtr), after the reify's contLab in
reifyArgumentsImpl (see lib/VM/JIT/x86-64/JitEmitter-array.cpp, which
carries a comment marking arm64 as still affected). No emitted-code
change.

Regression test to port or share: test/jit/x86-64/args.js's reifyTwice -
its a === b comparison is load-bearing (it selects the raw-bit tier the
stale type licenses); on x86-64 the type asserts trap without the fix.
arm64 currently has no test that flows a reified arguments object into a
type-sensitive emitter.
