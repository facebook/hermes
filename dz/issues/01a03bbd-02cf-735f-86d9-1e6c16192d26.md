Both backends (arm64 and x86-64), all heap modes, -O only. Silently wrong
values, not a crash.

Repro (committed as test/jit/try-catch-dest-reg.js, XFAIL on both arches):

    function f(o) {
      var y = "prior";
      try { y = o.throwingGetter; } catch (e) { return y; }
    }

The interpreter returns "prior"; the JIT returns 0 (the register-stack
zero-fill read back as a double).

Mechanism: before emitting a throwing instruction, emitters sync FR temps
to the frame but exclude the destination register
(syncAllFRTempExcept(frRes)), reasoning it is about to be overwritten. If
the instruction throws instead, the catch handler reads the destination's
frame slot, which still holds the _sh_enter zero-fill rather than the
variable's prior value. Plain calls are unaffected (callImpl syncs
everything, no exclusion), which is why nothing caught this earlier.
Neither -Xjit-emit-asserts nor -Xjit-emit-type-asserts can see it: the
stale value is well-typed.

Scope: 54 destination-excluding sites per backend (39 in the
"frRes != x ? frRes : FR()" ternary form, 15 unconditional), 108 across
both backends. The unconditional form has no operand-aliasing guard.

Likely fix shape: do not exclude the destination when isInTry() (or
narrow via liveness across the exceptional edge, if the register
allocator's liveness can answer that). Costs one store per instruction
only in try functions, which already have no global registers. Should
land on arm64 first or both together; the fix flips the XFAIL to XPASS
on whichever backend it lands, flagging itself in lit.

Found while un-gating test/jit for x86-64. Full notes: doc/JIT.md
("Confirmed bug" section) and the Delivered section of
doc/superpowers/specs/2026-08-23-x86-64-jit-design.md.
