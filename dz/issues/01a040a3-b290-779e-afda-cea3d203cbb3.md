Profiling benchmarks/react (pixel-grid.react-native-forget.js) on a
Release/clang x86-64 build (HV64, -Xjit, 80s run, perf -F 397, dwarf
call graphs), HadesGC::OldGen::search(unsigned) alone shows 25.1% SELF
time - a quarter of every cycle the program executes. The enclosing GC
work totals ~40%: youngGenCollection 35.7% inclusive, within which
scanDirtyCardsForSegment is 19.1% inclusive and EvacAcceptor
forwardCell ~19.9%. The allocation feeding it: JSObject::create 14.2%
inclusive, _sh_ljs_new_array 8.6%.

The same shape appears at lower intensity on pixel-grid-small (GC ~24%,
OldGen::search 7.6% self). The profiled runs executed from source via
the CLI; on the 80s run the in-process compile is <2.5% of samples, so
it does not distort the ranking. (Precompiled-HBC confirmation to be
attached during investigation.)

Why this looks anomalous rather than "GC is expensive": a freelist
search consuming 25% of a program suggests long walks per allocation -
fragmentation, a degenerate size-class distribution, or search being on
the per-promotion hot path during young-gen evacuation. It also lines
up with independent observations from the 2026-08-26 cross-engine
sweep: Hermes's competitive losses vs V8 Sparkplug / JSC Baseline are
exactly the allocation-churn workloads (this benchmark, Octane splay),
and HEAP_HV_PREFER32 - which halves heap size and therefore this
machinery's work - speeds this benchmark up 43% while other benchmarks
are largely insensitive.

Not yet investigated: what OldGen::search's caller mix is (promotion
during YG evac vs direct OG allocation), what the freelist/size-class
structure looks like under this workload, and whether the search is
algorithmically long (many cells per call) or merely called extremely
often. GC statistics and a precompiled-bytecode profile are the first
steps.

    Investigation complete (2026-08-27); root cause found and validated by a
    prototype fix. All measurements below are from PRECOMPILED bytecode
    (hermes -emit-binary), Release/clang x86-64, HV64.

    ROOT CAUSE. OldGen::search is first-fit over per-size-class buckets:
    32 small buckets at 8-byte granularity (so every cell in a small bucket
    has the identical size), then power-of-2 buckets. A cell can satisfy a
    request sz only if cellSize == sz or cellSize >= sz +
    minAllocationSize() (16 bytes here - two compressed pointers, heap-
    aligned; under HV32 it is 8, one HeapAlign, and there is no dead
    zone at all); anything in between is a "dead-zone" cell that can be
    neither taken nor split. When the exact-size bucket is empty,
    findNextSetBitFrom lands in the adjacent bucket, whose every cell is
    dead-zone by construction - and search walks it cell by cell, every
    call.

    EVIDENCE (scratch counters in search, pixel-grid React benchmark, one
    run): 18.7M calls walked 3.587 BILLION cells (avg 191.5/call), of which
    99.7% were dead-zone skips. Two request sizes dominate: 80-byte
    requests (13.7M calls, avg walk 213 - scanning the entire 88-byte
    freelist each time) and 24-byte requests (4.5M calls, avg 149).
    perf annotate agrees: 89% of search's self time is the two loads in
    the cell walk (header + next_). GC stats for the same run: 13.7 GB
    total allocation, 77 MB peak live, 6369 YG collections; totalGCTime
    was ~78% of the (stats-instrumented) run.

    FIX SHAPE (one guarded statement): a bucket strictly between
    bucket(sz) and bucket(sz + minAllocationSize()) cannot contain a
    usable cell, so when the exact bucket is empty, resume at
    findNextSetBitFrom(getFreelistBucket(sz + minAllocationSize())):

        size_t bucket = getFreelistBucket(sz);
        if (!freelistBucketBitArray_.at(bucket))
          bucket = freelistBucketBitArray_.findNextSetBitFrom(
              getFreelistBucket(sz + minAllocationSize()));

    Soundness: under HV64 exactly one small bucket is ever skipped, and
    small buckets hold exactly-sized cells, so it is provably all-dead
    for this request; under HV32 no bucket lies in between and nothing
    is skipped. A large bucket(sz), if nonempty, is still scanned
    exactly as before, and for large sizes sz + minAllocationSize() <=
    2 * sz bounds bucket(sz+minAlloc) at bucket(sz) + 1, which is where
    the scan resumes anyway once bucket(sz) is known empty - so nothing
    usable is ever skipped. Any cell found at bucket >=
    bucket(sz+minAlloc) in the small range is guaranteed splittable, so
    walks become O(1) there.

    VALIDATION BY CURE (same instrumented build + fix): total walked cells
    3.587B -> 20.6M (174x); every small bucket avg walk 1.0; the only
    residual walker is the first mixed-size large bucket (256-511B, 2.5M
    iters = 0.06% of the original).

    CLEAN A/B (uninstrumented fix-only binary vs pristine baseline,
    interleaved runs, precompiled bytecode):
      pixel-grid -Xjit:  7361/7581  -> 11049/10957  (+47%), wall 71-73s -> 48.5-48.9s
      pixel-grid interp: 5743       -> 8252         (+44%)
      pixel-grid-small -Xjit: 127238/122650 -> 139502/135744 (+10%)
      Octane splay -Xjit: 6449/6519 -> 6120/6674    (no change; splay's GC
        cost is a different mechanism, not this one)
    The fix also removes the long-observed HV64 run-to-run instability on
    pixel-grid (fixed runs within +/-0.8%; instability was fragmentation-
    state sensitivity of the dead-zone walks). Context: HV64+fix (11049)
    now matches HV32-without-fix (10784) and closes most of the gap to V8
    Sparkplug (12781) on this benchmark.

    Status: prototype fix is in the working tree (lib/VM/gcs/HadesGC.cpp,
    uncommitted); full ASan check-hermes validation run in progress.
    Remaining for a real landing: decide the destination branch (this is a
    GC change, not JIT - it does not belong on x86-jit topically), a
    regression test strategy (the effect is performance, not correctness;
    possibly a gtest asserting search's walk behavior via a synthetic
    freelist), and whether large-bucket walks deserve the same treatment.
